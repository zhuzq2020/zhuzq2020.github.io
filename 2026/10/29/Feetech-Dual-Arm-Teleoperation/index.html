TECH NOTE 2026.10.29

基于飞特舵机的双臂遥操作系统实践：从关节采集到 WBC 对接

约 11 分钟阅读 5059 字 # 机器人# 遥操作# 飞特舵机# MuJoCo# WBC
READING Z / 26

做机械臂遥操作，最开始想到的通常是：读取主臂角度，再把角度发给从臂。但真正接入设备后，会发现角度只是这条链路中的一个环节。编码器零点、关节方向、模型限位、采样时序和网络状态，都决定了从臂收到的目标是否可信。

最近，我围绕飞特 STS3215-C046 舵机搭建了一套双臂遥操作控制程序。主臂每侧使用八个舵机，其中七个映射到机械臂关节，第八个作为夹爪输入；上位机负责串口采集、模型映射和网络传输，WBC 端负责接收目标并连接从臂控制系统。

这篇文章记录其中值得复用的设计和调试经验。内容集中在终端控制、模型标定与网络遥操作，当前仍有串口稳定性和实机跟随效果需要继续验证。

1. 先明确系统中各部分的职责

主臂是操作者用手推动的输入设备，从臂是执行运动的机器人手臂。两者的机械尺寸、零位和允许运动范围可以不同，因此需要在中间建立明确的角度映射。

这个分工让主臂采集和机器人控制可以分别调试：先确认主臂反馈与模型一致，再接入网络，最后验证从臂执行。

2. 双臂使用两条独立总线

每侧串口连接 ID 1–8，波特率为 1 Mbps。左右总线互相独立，因此两侧可以使用相同的一组舵机 ID。

项目 当前设计
舵机 STS3215-C046，单圈位置模式
每侧数量 8 个
机械臂映射 ID 1–7
夹爪输入 ID 8
编码器周期 4096 刻度
串口目标采样率 30 Hz
串口分配 每侧独立设备、独立工作线程

左右设备通过 /dev/serial/by-id/ 固定绑定，避免重启或重新插拔后 ttyUSB0、ttyUSB1 编号交换。固定标识跟随 USB 转串口设备，所以线缆与实际左右臂的对应关系仍需要在现场确认。

另一个重要约束是串口所有权。运行期间，每条串口由对应的工作线程统一读写，终端命令和网络请求通过队列提交。这样可以避免多个线程交叉收发，破坏“请求—应答”的对应关系。

3. 把舵机刻度转换为模型角度

其中：

  • raw 是舵机实际反馈刻度。
  • direction 为 +1 或 −1，描述编码器增加方向与模型正方向的关系。
  • offset 是当前模型的角度偏移，公式中采用弧度。
  • q 是映射后的模型关节角，单位为弧度。

例如，raw=2304，相比中位增加了 256 刻度，对应输出轴转角为 22.5°。若方向为 +1，而这一个实体姿态需要对应模型的 0°，就应设置 −22.5° 的模型偏移。

这里容易出现一个错误：把输出轴角度再除以舵机内部减速比。 当前编码器反馈按输出轴每圈 4096 刻度使用，换算时不再除以 147。

跨越 4095→0 时，还需要结合模型关节范围选择等价角度，避免显示突然跳一整圈。项目利用编码器周期和模型限位处理这一问题；这种方法依赖关节范围能够消除歧义，不能直接推广到任意多圈关节。

4. 硬件标零与模型标定分开处理

同一套主臂要适配同川和珞石模型，不能每切换一次模型就重新写舵机零点。我将标定分成了三个层次。

层次 调整内容 影响范围
硬件标零 修改舵机 EEPROM 偏移，将参考位置设为中位 使用该实体舵机的所有模型
方向配置 设置反馈到模型的正负方向 当前模型配置
模型偏移 将某个实体参考姿态对应到已知模型角度 当前模型配置

硬件标零用于确定实体设备的基准，模型偏移用于适配不同机器人的参考姿态。切换模型时，优先调整后两项。

只有实体姿态确实对应模型全零时，才适合使用 align all。零位标定准确、关节方向一致，也只能说明关节映射成立；不同尺寸机械臂的末端轨迹仍可能不同。

5. 用 MuJoCo 检查映射结果

项目保留了真实网格和关节结构，并提供同川、珞石等模型配置。实体反馈到来后，将映射后的角度写入 MuJoCo 的 qpos，再调用 mj_forward 更新姿态。

这一过程用于观察实际关节反馈在模型中的表现，不进行电机动力学预测。

调试时，我先保持主臂卸力，逐个关节手推，检查三个问题：

  1. 动的是不是预期关节，左右臂有没有接反。
  2. 模型旋转方向是否与实体一致。
  3. 参考姿态和限位附近的显示是否合理。

模型能把配置错误直观地暴露出来。例如，一个关节方向写反，可能在小角度时不明显，但逐轴手推后就容易发现。实际反馈超过模型范围时仍照实显示，不能将反馈截断成一个看似正常的姿态。

模型预览和无窗口控制也分开提供：前者完全离线，后者仍连接实体并执行反馈采集，只是不打开查看器。

同一串口的多轴位置目标通过 SDK 同步写组包，一帧包含多个 ID 的目标。未指定的轴不补发旧目标，任一目标非法时整批拒绝。

双臂命令会先统一校验两侧目标、连接、扭矩状态和队列容量，再提交给两个串口线程。但左右臂最终仍在不同总线上分别发包，因此这里没有跨串口硬件同步触发，也不能保证机械上严格同时起动或到达。

同步写广播没有逐舵机应答。发包成功之后，还需要通过实际位置反馈确认执行情况。项目另有单舵机普通写入口，可以等待该 ID 的应答，但应答成功同样不代表机械轴已经到位。

7. 30 Hz：区分采样、发送和执行

项目的串口目标采样率为 30 Hz，约每 33.3 ms 读取一轮。但“系统是 30 Hz”这个表述不够准确，至少需要区分四个环节。

环节 含义
串口采样 完成一轮舵机位置读取
网络发送 将最新状态快照传给 WBC 桥接
桥接输出 将有效目标交给 WBC
从臂执行 控制器实际消费目标并驱动机器人

串口线程逐个读取舵机，因此一轮八轴反馈不是同一时刻采集的。当前 status 中的位置反馈频率由相邻两轮采样完成时间计算：

网络端也需要保留源采样的新鲜度。刚收到一个 TCP 包，只能说明报文刚到，不能说明其中的关节数据刚采集。项目同时关注采样年龄、序号和通信状态，避免把积压旧帧作为新目标继续使用。

8. 网络遥操：对齐之后再进入跟随

WBC 桥接通过 TCP 接收主臂数据，再转换为机器人控制侧的关节目标。网络连接建立后，系统还需要确认关节顺序、模式和反馈状态，才进入实际遥操作。

对齐过程会驱动所选从臂。进入 READY 表示满足当前模式的对齐条件；输入 start 后才开始跟随。

另一类模式用于让主臂对齐后保持上力，其验收后进入 HOLDING，保持目标姿态，并不输出 WBC 跟随流。这两类模式用途不同，两端必须使用匹配的配置。网络对齐命令与前面的软件零位标定命令虽然同名为 align，作用也完全不同。

主从限位不一致时，可以显式启用目标裁剪：保留主臂实测角度，同时将发送目标裁剪到主臂模型与 WBC 有效范围的交集。这样才能解释“主臂继续推，但从臂停在边界”的现象。裁剪后的控制目标需要与原始测量分开记录。

主动推送与最新值缓存

除请求应答外，项目还实现了可选的主动推送。主臂网络线程读取最新快照发送，WBC 端保存最新缓存并按周期输出，应用层不逐帧排队回放历史动作。

需要注意，缓存重用不能重置源数据年龄，也不能产生新的采样序号。调度迟到时跳过错过的周期，避免突然追发一串旧目标；TCP 本身的顺序传输和重传特性仍然存在。

已有两台电脑之间的模拟端点测试，在人为延后心跳处理的条件下，4 秒稳态窗口的新帧接收与关节输出约为 29.99 Hz。这说明通信结构具有继续联调的基础，尚不能据此推导真实机器人端到端延迟。

10. 一次串口异常带来的排查经验

联调中曾出现这样的报错：

随后网络客户端退出，WBC 才报告 TCP 断开。如果只看最后一条日志，很容易把故障归到网络层。

按时间顺序检查后，可以确认最早的异常发生在主臂串口应答阶段。它表明 SDK 收到的状态包无法通过检查，现有日志还不足以区分接线、供电、应答时序等原因，更不能直接证明舵机损坏。

这次排查让我更重视日志中的几个字段：侧别、舵机 ID、具体操作、请求值、通信错误，以及最后一份有效反馈的年龄。只有将这些信息串起来，才能判断故障起点和后续连锁结果。

扭矩写入结果未知时，也不能根据“程序已经退出”推定设备已经卸力。设备状态需要依靠回读确认，失联情况下则无法仅凭软件保证。

11. 与 OpenArm Mini、SO-101 的关系

这套七轴加夹爪的主臂形式，与 Open Arms Mini 的硬件配置高度吻合。其上游方案每侧使用八个 STS3215-C046 舵机，定位也是机器人遥操作主手。不过，现有本地机械模型缺少明确的来源声明，机械设计是否直接参考该项目，还需要原始 CAD 或设计记录确认。Open Arms Mini 上游项目

飞特舵机也出现在 SO-101 生态中。SO-101 官方物料表包含 C001、C044、C046 等不同规格；现有 C046 可以考虑复用于采用该规格的主手关节，但一整套 C046 不能直接视为标准 SO-101 的等效配置。更换结构后仍要重新确认供电、装配、关节映射和标定。SO-101 官方项目

这也提供了后续扩展方向：沿用已经建立的采集、标定和状态诊断能力，再对接 LeRobot 的示教数据采集流程。目前项目尚未完成 SO-101 接入或模仿学习训练。

12. 当前进展与下一步

目前，终端控制、双臂配置、模型映射、软件标定和 WBC 网络桥接已经形成实现基础；主动推送、目标裁剪及夹爪输入也有离线或模拟测试记录。

接下来最值得投入的是三项验证：串口与扭矩切换的长期稳定性、主臂采样到从臂响应的端到端时延，以及不同姿态下的实际跟踪误差。它们能帮助判断现有系统在哪些条件下工作可靠，以及下一轮优化应落在串口采集、网络调度还是机器人控制侧。

对我而言，这个项目最有价值的积累，是把编码器反馈、模型角度、网络目标和机器人执行之间的关系逐一明确下来。每层都有可检查的数据和状态，后续适配其他主臂或从臂时，才有稳定的基础可以复用。
